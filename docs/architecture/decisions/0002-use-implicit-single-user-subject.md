# ADR 0002：V5 使用隐式单用户主体

- 状态：已接受
- 日期：2026-08-24

## 背景

V5 需要让显式记忆稳定归属于同一个用户，并在跨会话读取、纠正、禁用和删除时保持一致。当前 ContextPilot 是本机或可信网络中的单用户应用，没有登录、注册、角色或多租户边界。

完整登录可以提供身份认证，但同时会引入账号生命周期、凭据安全、Session、CSRF、授权过滤、数据迁移和页面流程。V5 的首个用户场景是验证可控长期记忆，而不是交付账号系统；让登录成为前置条件会把当前学习目标扩大为另一条产品主线。

## 决策

V5 第一阶段引入稳定的隐式本地用户主体，但不实现登录：

- PostgreSQL 保存一条不可由普通业务删除的本地用户记录，使用稳定 UUID 和固定业务键 `LOCAL_OWNER`；
- 后端通过 `CurrentSubjectProvider` 获取当前主体，第一阶段唯一实现始终返回 `LOCAL_OWNER`；
- 用户记忆必须保存服务端解析出的 `owner_user_id`，API 请求体、查询参数和请求头均不接受客户端指定用户 ID；
- 隐式主体只解决稳定归属和未来替换缝隙，不宣称身份认证、访问控制或多用户隔离；
- 当前部署继续限定在本机或可信网络。只要实例可能被不受信任的人访问，登录与资源授权就成为发布前置条件；
- 未来加入 Spring Security Session 或 OIDC 时，用新的 `CurrentSubjectProvider` 适配器映射到同一应用用户 ID，并显式决定现有 `LOCAL_OWNER` 数据如何绑定；不得使用易失的 HTTP Session ID 作为业务所有者 ID。

V5 第一阶段不为现有知识库、会话、文档、Action 或 Research 宣称多用户隔离。它们仍属于当前单用户安装；用户记忆通过稳定主体归属，为未来完整所有权迁移保留清晰入口。

## 结果

- V5 可以在不引入登录系统的情况下验证显式记忆场景；
- 记忆业务代码不需要写死 UUID，也不依赖浏览器状态；
- 所有能访问实例的人仍被视为同一个用户，不能把当前实现部署成多用户服务；
- 将来增加登录时仍需为知识库、会话和其他根资源设计所有权迁移与授权过滤，本 ADR 不把该工作伪装成已经完成；
- 不新增 Spring Security、JWT、OIDC 或密码相关生产依赖。

## 暂不选择

- 完整注册和登录：会阻塞当前显式记忆场景，并扩大为账号安全项目；
- 浏览器生成或提交用户 ID：客户端可伪造，且清除浏览器数据后身份会漂移；
- 使用 HTTP Session ID 作为所有者：Session 会轮换和过期，不能作为持久业务身份；
- 完全不建用户主体：会把单例假设散落到记忆服务，未来难以替换。
