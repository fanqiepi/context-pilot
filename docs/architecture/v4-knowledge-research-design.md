# V4 知识研究助手详细设计

> 状态：第一阶段整体授权实施；受限编排方向确认日期：2026-08-16；Slice 1 完成、固定维度/逐文档生产基线与 Slices 2-7 整体授权日期：2026-08-17；前置基线：V1、V2、V3 已完成并通过验收。

## 1. 文档目的

本文把 V4“知识研究助手”从路线方向细化为可评审的产品和技术方案。V4 的目标不是把 ContextPilot 改造成能够无限自主思考的通用 Agent，而是在现有 `KNOWLEDGE_QA` 边界内，为确实需要多个受控检索步骤的知识任务提供可解释、可中止、可评估的确定性编排。

本次讨论已经确认采用 **固定维度/逐文档确定性编排** 作为 V4 第一阶段生产范式，并完成产品、计划、预算、证据、状态、数据、API/SSE 和评估合同确认。Slice 1 已证明范围化多步检索的必要性，同时证明模型 Planner 在固定案例上没有质量收益且成本更高。Slices 2-7、生产代码、Flyway、正式 API/SSE、前端和最终验收已整体授权；切片保持顺序实施和独立验证，但不再作为重复授权门。

## 2. 问题与目标

当前 `KNOWLEDGE_QA` 是一次检索、一次证据校验、一次回答生成的固定链路。它适合事实问答，但面对“比较多份文档”“按多个维度整理主题”“生成有来源的学习提纲”等任务时，单个查询的 Top-K 结果可能不能覆盖全部子问题，最终只能遗漏关键证据或拒答。

V4 第一阶段只解决一个问题：用户在同一知识库中显式选择多份文档，指定比较问题或维度，系统生成逐项可追溯的多文档比对。指定文档摘要、主题概览和学习提纲不属于第一阶段目标，也不因本设计获得实施授权。

该任务必须保留知识库隔离、来源约束、引用、拒答、SSE、历史、trace ID 和可重复评估。规划只用于拆分只读知识任务，不产生业务副作用。

## 3. 已确认的设计决策

1. 顶层路由继续使用 `KNOWLEDGE_QA`，不新增 `AGENT` 或 `RESEARCH` 顶层能力。
2. 普通问答继续走现有单轮 RAG。只有明确进入知识研究任务时才启用多步编排。
3. 研究任务采用“固定维度生成完整计划，再按计划逐文档执行，再统一综合”的确定性编排；首版不采用模型 Planner 或 ReAct 的逐步思考—行动循环。
4. 计划必须转换为服务端定义的强类型结构，并经过范围、步骤数、查询长度和预算校验。模型文本不能直接成为可执行指令。
5. 执行器首版只允许调用现有受控检索能力及必要的应用内证据整理，不允许任意 SQL、Shell、文件、HTTP、MCP 或业务动作。
6. 首版不自动重规划，不根据中间结果无限追加步骤，也不引入 LangGraph、Agent 框架或外部工作流运行时。
7. 不保存或展示模型的隐藏思维过程。系统只保存可审计的任务目标、结构化计划、步骤状态、检索范围、证据引用、预算使用和安全错误摘要。
8. 无足够证据时必须在整体或局部明确说明材料不足；不得以增加步骤为由降低 grounded RAG 的拒答标准。

## 4. 范围与非目标

### 4.1 第一阶段设计范围

- 通过显式“多文档比对”模式选择资料范围，不使用自然语言自动路由；
- 生成版本化、强类型、可校验的研究计划；
- 按计划顺序执行有限的只读检索步骤；同一步骤内对冻结文档做有界并行检索，并按原文档顺序汇总；
- 建立跨步骤证据账本，去重并保留文档与 chunk 来源；
- 综合多步结果并对最终陈述生成可验证引用；
- 持久化任务与步骤状态，支持查询、历史恢复和取消；
- 通过 SSE 展示计划摘要、步骤进度、最终回答与引用；
- 建立与现有单轮 RAG 对照的固定评估集。

### 4.2 明确不包含

- 开放式 ReAct、自主循环、自我修改目标或不受限重规划；
- 多 Agent、角色协作、并行自治研究；
- 通用 Skill/工具注册表、动态工具发现或任意工具调用；
- MCP、互联网搜索、外部 SaaS、任意文件系统或代码执行；
- 模型生成或执行 SQL；
- 任何产生副作用的业务动作或动作链；
- 长期用户记忆；
- 扫描 PDF OCR、跨知识库检索、多用户权限模型；
- 保存 chain-of-thought 或把中间自然语言推理当成审计记录。

## 5. 第一阶段纵向场景（已确认）

第一阶段唯一可验收场景为：**用户在一个知识库中显式选择 2 至 5 份文档，指定比较问题，系统生成带逐项引用的多文档比对**。文档数量上限固定为 5，用户不单独填写比较维度；服务端从版本化固定维度目录中确定性识别最多 4 个维度，未命中时以原问题生成一个兜底步骤。

选择该场景的原因是：它能直接验证一次 Top-K 是否遗漏某份文档、规划是否覆盖各比较维度、文档范围是否被严格执行，以及综合结果中的引用能否支持对应结论。它比开放式“帮我研究一下”更容易定义正确答案和失败语义。

第一阶段不同时交付单文档摘要、主题概览或学习提纲，也不通过自然语言猜测进入研究编排。以后增加其他知识任务需要新的范围评审，不能仅复用已有枚举或前端入口即视为获批。

## 6. 用户交互原则

- 用户必须在一个知识库中选择 2 至 5 份文档，并填写必填比较问题；比较维度由版本化固定目录确定性识别，不增加单独的结构化维度输入。
- 只有未删除、`SUCCEEDED` 且 `embeddingIndexCompatibility = CURRENT` 的文档可以选择。`PENDING/PROCESSING` 提示等待，`FAILED` 提示可用的重试入口，`UNKNOWN/OUTDATED/NOT_INDEXED` 提示重建索引。
- 启动时重新校验全部选中文档；任一文档失效即整体拒绝，不静默排除或扩大范围。
- 前端在普通问答之外提供显式“多文档比对”模式；普通聊天文本永远不会自动触发研究运行。
- 计划生成并校验成功后自动执行，不等待二次确认；用户可以取消活动运行。
- 系统展示可读计划和步骤进度，但不展示隐藏推理提示词。第一阶段最终结果不生成表格，以文本段落或条目表达比较结论并绑定引用。
- 某个步骤—文档组合没有有效证据时，只允许单独使用固定句式“`文件名`：本次检索未找到相关内容。”；该句式中的文件名必须属于本次所选文档，不需要引用，也不能扩写为对文档内容的推断或使用其他文档代替。
- 取消后允许重新执行，但必须创建新的研究运行并保留旧记录。SSE 是用户入口；同步接口只用于集成测试。
- 刷新页面后从持久化状态恢复计划、进度和最终结果，不重新执行已完成步骤。

## 7. 受限 Plan-and-Execute 流程

```mermaid
flowchart LR
    A["研究请求"] --> B["范围与输入校验"]
    B --> C["固定编排器生成强类型计划"]
    C --> D["计划校验与预算冻结"]
    D --> E["有界步骤执行器"]
    E --> F["证据账本"]
    F --> G["Synthesizer 综合回答"]
    G --> H["引用与范围校验"]
    H --> I["完成、部分完成或拒答"]
```

1. **输入校验**：确认知识库、会话、任务类型、文档范围和用户问题可信关联。
2. **规划**：固定编排器依据版本化维度目录生成计划 DTO，不调用模型、检索或业务动作。
3. **计划校验**：服务端验证计划版本、步骤上限、查询长度、文档范围和总预算；失败时不进入执行。
4. **执行**：步骤之间按稳定顺序执行；同一步骤内以有界线程池并行调用受控检索服务，完成顺序不影响按原文档顺序汇总。每步只能使用冻结后的知识库和文档范围。
5. **证据账本**：记录命中的文档、chunk、相似度、受限摘录、步骤来源和去重结果，不让模型伪造引用 ID。
6. **综合**：只向 Synthesizer 提供经过校验和裁剪的证据；输出需要能映射到证据账本。
7. **最终校验**：检查引用存在、范围正确、证据覆盖和任务状态，再完成助手消息。

## 8. 强类型计划合同

第一阶段内部合同固定为：

```text
ResearchPlan
- planVersion       // 服务端固定为 v1
- taskType          // 服务端从请求取得，固定 DOCUMENT_COMPARISON
- steps[]

ResearchStep
- stepId           // 服务端生成 UUID
- ordinal          // 服务端按数组顺序生成
- goal             // 固定编排器生成，用于展示步骤目标
- query            // 固定编排器生成，用于检索
- documentIds[]    // 固定为全部冻结文档
```

固定编排器生成 `steps[].goal/query/documentIds`，服务端补充版本、任务类型、步骤 ID 和顺序。版本化目录按问题中最早出现的别名排序并去重：识别 1 至 4 个维度时每个维度生成一个步骤；未识别时以规范化原问题生成一个步骤；识别超过 4 个维度时返回 `RESEARCH_PLAN_INVALID`，不静默丢弃。每个步骤覆盖全部冻结文档，确保逐文档执行与范围完整性。第一阶段不保存 `objective`、`stepType` 或 `required`；所有步骤都是顺序执行的只读检索步骤。

计划校验至少包含：

- 步骤数量为 1 至 4；
- `goal`、`query` 和 `documentIds` 非空且长度受限；
- 每步文档范围是用户选择范围的子集，全部步骤的文档并集必须等于用户选择范围；
- 规范化后相同的 `query + documentIds` 不得重复；
- 总预算在计划执行前冻结，模型不能扩大预算。

固定编排不涉及模型 JSON 解析或结构修复。计划校验失败时直接结束运行，不回退到模型规划或无约束执行；第一阶段不允许自动重规划。

## 9. 已确认预算与循环上限

| 预算项 | 第一阶段固定值 |
| --- | ---: |
| Planner 调用 | 0 次；固定编排不调用模型 |
| 计划步骤 | 最多 4 步 |
| 检索调用 | 每个步骤按目标文档分别检索 1 次，执行器提交前再次强制最多 20 次 |
| 每文档 Top-K | 3 |
| 原始命中 | 最多 60 个 chunk |
| 全任务保留证据 | 最多 24 个去重 chunk、24000 字符 |
| 单条证据摘录 | 最多 1000 字符 |
| 每步骤证据 | 最多 8000 字符 |
| Planner/结构修复输出 | 0 Token |
| Synthesizer 输出 | 最多 3000 Token |
| 最终回答正文 | 最多 1800 字符；超限时按完整行回退并记录 `RESEARCH_ANSWER_BUDGET_REACHED` |
| Synthesizer 调用 | 1 次 |
| 自动重规划 | 0 次 |
| 端到端硬超时 | 90 秒 |

> 2026-08-21 临时诊断例外：DeepSeek V4 默认 Thinking 模式会将推理 Token 计入 `max_tokens`。为验证空正文是否由 3000 Token 被推理过程耗尽导致，研究综合暂不发送请求级 `max_tokens`；90 秒硬超时、单次模型调用和 1800 字符最终正文上限保持不变。该例外不是发布合同变更，发布门验证前必须依据真实模型证据恢复或重新批准生成预算。

证据裁剪先为每个“步骤 × 文档”组合保留相似度最高的一条有效证据，再按相似度补充剩余名额。达到任一硬上限后停止新增工作：已有有效结论时返回部分结果，没有有效结论时失败，不得静默突破预算。

## 10. 已确认状态与失败语义

运行状态与回答结果分开保存：

```text
executionStatus:
PLANNING -> EXECUTING -> SYNTHESIZING
         -> SUCCEEDED | PARTIAL | FAILED | CANCELLED

answerStatus:
ANSWERED | REFUSED | null
```

允许的终态组合为 `SUCCEEDED + ANSWERED`、`SUCCEEDED + REFUSED`、`PARTIAL + ANSWERED`、`FAILED + null` 和 `CANCELLED + null`：

- `SUCCEEDED + ANSWERED`：所有步骤和引用校验正常完成，至少有一个有效比较结论；合法的“`文件名`：本次检索未找到相关内容。”不降低状态。
- `SUCCEEDED + REFUSED`：所有步骤正常完成，但没有足够证据支持用户问题。
- `PARTIAL + ANSWERED`：存在有效结论，但发生单文档检索失败、无效引用被删除、预算耗尽或超时；回答必须说明未完成范围。
- `FAILED`：计划修复后仍无效、没有任何检索成功、Synthesizer 失败或无法解析、持久化失败，或超时且没有有效结论。
- `CANCELLED`：用户取消活动运行；停止后续步骤，迟到的模型结果不得持久化为最终回答。

步骤状态固定为 `PENDING/RUNNING/SUCCEEDED/PARTIAL/FAILED/CANCELLED`。没有命中证据不是技术失败；单文档检索失败时继续其余工作并使运行进入 `PARTIAL`，全局 Embedding、数据库或模型依赖不可用时立即失败。90 秒超时后，有有效结论则部分完成，否则失败；使用稳定错误码记录原因，不增加 `TIMED_OUT` 状态。

状态只能通过条件更新单向迁移。只有活动运行可以取消；完成与取消并发时先写入终态的一方获胜。重新执行始终创建新运行，并通过可空 `retryOfRunId` 关联原运行。

## 11. 检索范围与证据账本

现有 `RetrievalService` 在不破坏普通问答合同的前提下增加单文档范围检索。每次调用同时过滤会话知识库、一个冻结 `documentId` 和当前 Embedding profile，并再次依赖逻辑删除、处理成功状态、Top-K、`0.5` 相似度阈值和受限返回字段。一个步骤按其每个目标文档分别检索，避免全局 Top-K 被单一文档占满；同一步骤内默认最多 4 个检索并行，合法配置范围为 1 至 5，所有结果按冻结文档列表的固定顺序进入证据账本。任务在并行提交前预留调用预算，实际开始的调用和预留任务分别计数，二者都不得突破 20 次上限。

证据账本以真实检索结果为唯一来源：

- 使用真实 `vector_store.id` 去重；同一 chunk 被多个步骤命中时只保存一份证据；
- `research_evidence.id` 由服务端生成，保存 vector ID 快照、文档、chunk、页码、Embedding profile、相似度和受限摘录；
- 不对可重建的 `vector_store` 建外键，历史证据不受索引重建影响；
- 通过 `research_step_evidence` 保存步骤—证据多对多关系、步骤内排名和相似度；
- 每个事实性结论或段落至少绑定一个当前运行的证据 ID；只有严格匹配所选文件名的“`文件名`：本次检索未找到相关内容。”可无引用保留且不降低状态。不存在或越界引用对应的结论被删除，仍有有效结论时为 `PARTIAL`，否则为 `REFUSED`；
- 第一阶段不增加 Synthesizer 修复调用。

## 12. 模块边界

V4 仍使用模块化单体和显式 Java 应用服务。第一阶段使用独立 `research` 业务能力包，由 `chat` 总入口编排，不增加新的顶层能力路由：

- `ResearchApplicationService`：创建运行、冻结范围、驱动状态迁移和完成助手消息；
- `DeterministicResearchPlanner`：按版本化维度目录生成强类型固定计划；
- `ResearchPlanValidator`：纯确定性校验和预算计算；
- `ResearchExecutor`：按顺序执行固定步骤并响应取消；
- `ResearchEvidenceLedger`：证据去重、裁剪和可信 ID；
- `ResearchSynthesizer`：基于证据账本生成最终内容；
- `ResearchRunRepository`：任务、步骤和证据的持久化端口；
- `ResearchStreamPublisher`：把已持久化状态转换为 SSE 事件。

这些都是领域化组件，不是通用 Agent runtime 或工具网关。首版采用显式循环即可；只有后续评估证明恢复、分支或并行需求使应用服务不可维护时，才重新评估工作流框架。

## 13. 已确认数据模型

第一阶段新增四类审计型业务记录，全部使用 UUID、带时区时间和逻辑删除：

### `research_run`

- 关联知识库、会话、用户消息和最终助手消息；
- 保存客户端幂等请求 ID、任务类型、计划版本和 2 至 5 个冻结文档 ID 的受限 JSONB 数组；
- 保存执行状态、回答状态、预算上限与实际使用、当前步骤、稳定错误码、安全错误摘要和 trace ID；
- 使用可空 `retry_of_run_id` 关联重新执行来源；
- 保存开始、取消、完成和创建更新时间；
- 一个助手消息最多关联一个活动研究运行。

原始问题继续由关联用户消息保存，不重复保存；固定编排没有原始模型 JSON 或隐藏思维，计划通过规范化步骤恢复。

### `research_step`

- 关联研究运行并保存稳定顺序；
- 保存目标、检索查询和受限 `document_ids` JSONB 数组，不保存固定的步骤类型或 `required`；
- 保存状态、命中数量、裁剪数量、耗时和安全错误摘要；
- 同一运行内 `ordinal` 和 `step_id` 唯一。

### `research_evidence`

- 关联研究运行和文档，保存 `vector_store.id` 快照、chunk、页码、相似度、受限摘录和 Embedding profile；
- 不对 `vector_store` 建外键；同一运行内同一真实 vector ID 只能有一条活动证据。

### `research_step_evidence`

- 关联步骤和证据，保存步骤内排名和相似度；
- 同一步骤与证据组合唯一；
- 支持同一证据被多个步骤命中，不在 JSON 中维护步骤 ID 数组。

`message_citation` 增加可空 `research_evidence_id`；V4 引用必须关联当前运行的真实研究证据，V1-V3 历史行保持为空且不回填。`chat_message` 增加 `CANCELLED` 状态，只用于已取消的研究助手消息；`PARTIAL` 和 `REFUSED` 仍保存为已完成消息，由研究运行状态表达细分结果。

应用启动时将遗留 `PLANNING/EXECUTING/SYNTHESIZING` 运行标记为 `FAILED`，错误码为 `RESEARCH_RUN_INTERRUPTED`；第一阶段不自动恢复执行。研究记录不提供公开删除或隐藏 API。

## 14. API 提案

普通 `/api/chat` 与 `/api/chat/stream` 请求保持兼容。SSE 是用户入口，同步接口只用于集成测试。显式多文档比对请求增加强类型 `research` 对象：

```json
{
  "knowledgeBaseId": "uuid",
  "conversationId": "uuid-or-null",
  "question": "比较这些文档在部署方式和限制上的差异",
  "research": {
    "clientRequestId": "client-generated-uuid",
    "taskType": "DOCUMENT_COMPARISON",
    "documentIds": ["uuid-a", "uuid-b"]
  }
}
```

缺少 `research` 时行为与 V1-V3 完全一致，服务端不得根据 `question` 自动补出 `research`。`clientRequestId` 由前端生成并在活动记录中唯一；相同 ID 与相同规范化请求返回已有运行，相同 ID 携带不同请求返回冲突。`taskType` 只接受 `DOCUMENT_COMPARISON`；`documentIds` 必须包含 2 至 5 个不重复 ID。服务端不接受客户端计划、预算、证据或工具名称。

固定补充只读与取消资源：

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| `GET` | `/api/research-runs/{id}` | 返回运行状态、回答状态、冻结文档、计划步骤、预算/usage、错误摘要和最终消息关联 |
| `POST` | `/api/research-runs/{id}/cancel` | 原子取消活动运行并返回最新状态；已取消重复请求幂等成功，其他终态返回 `409` |

研究运行必须通过其会话和知识库关系验证访问范围。第一阶段不增加单独创建运行的 POST 接口：聊天请求原子创建用户消息、助手消息和运行。稳定错误码固定为 `RESEARCH_REQUEST_INVALID`、`RESEARCH_REQUEST_ID_CONFLICT`、`RESEARCH_DOCUMENT_NOT_FOUND`、`RESEARCH_DOCUMENT_NOT_ELIGIBLE`、`RESEARCH_RUN_NOT_FOUND`、`RESEARCH_RUN_NOT_CANCELLABLE`、`RESEARCH_PLAN_INVALID`、`RESEARCH_TIMEOUT`、`RESEARCH_DEPENDENCY_UNAVAILABLE` 和 `RESEARCH_RUN_INTERRUPTED`。

## 15. SSE 与历史恢复提案

研究流固定使用以下顺序：

```text
message
-> route
-> research_plan
-> research_step*
-> delta*
-> citation*
-> usage?
-> done(COMPLETED|PARTIAL|REFUSED|FAILED|CANCELLED)
```

- `research_plan`：运行 ID、任务类型、可读目标、步骤摘要和预算上限；
- `research_step`：步骤 ID、顺序、状态、目标、命中与裁剪数量、安全失败摘要；
- `delta`：仅用于最终综合回答，不流式展示 Synthesizer 中间内容；
- `citation`：只来自已保存证据账本；
- `usage`：汇总固定编排、检索和 Synthesizer 的可公开计量；
- `done`：包含 `COMPLETED/PARTIAL/REFUSED/FAILED/CANCELLED`、运行 ID 和 trace ID。

所有事件携带运行内单调 `sequence`。数据库状态是事实来源；SSE 断开不会取消或创建第二个运行，任务继续在有界执行器内运行，取消必须调用独立接口。历史消息只返回可空 `researchRun` 摘要，完整步骤通过运行查询接口读取；旧消息返回 `null`。刷新后如运行仍活动，前端轮询运行查询接口直至终态，第一阶段不提供 SSE 续传。

## 16. 安全边界

- 上传文档、用户问题和 Synthesizer 输出都视为不可信数据。
- 文档中的“忽略规则”“调用工具”等提示注入内容只能作为被引用资料，不能改变计划预算、系统指令或允许能力。
- 固定编排器只能产生只读检索步骤 DTO；执行器使用显式参数，不使用反射调用。
- 知识库、文档范围、Embedding profile、预算和 trace ID 都由服务端冻结；客户端或模型不能覆盖。
- 日志不记录完整私密文档、完整 Prompt 或模型隐藏推理；错误只保存脱敏摘要。
- 研究任务是只读能力，不复用 `action_request`，也不得借研究步骤触发 V2/V3 业务动作。

## 17. 评估与验收策略

V4 已先针对多文档比对建立“现有单轮 RAG”与“受限范围化多步检索”的对照评估，再选择固定编排进入完整实现。数据集必须持续包含能稳定证明多步检索收益的比较任务，不能只凭架构偏好扩大编排。

第一版固定数据集包含 32 个语义案例：8 个单轮 RAG 已足够的对照案例、12 个确需多步覆盖的比较案例、4 个局部缺失案例、4 个全局无依据案例和 4 个提示注入/范围隔离案例；另建立至少 12 个真实生命周期案例覆盖资格失效、固定计划校验、局部检索失败、取消、超时、幂等重复、SSE 断开、历史恢复和应用重启。代表性 8 个模型案例各重复运行 3 次检查稳定性。

通过阈值固定为：

- 显式入口正确率、选中文档覆盖率、越界文档命中率、预算超限率和生命周期幂等案例均为 100% 通过，其中越界命中和预算超限的允许数量为 0；
- 固定编排计划 schema 有效率为 100%；
- 多步子集任务完成率和比较维度覆盖率不低于 85%，且任务完成率相对单轮 RAG 至少提升 15 个百分点；
- 引用正确率不低于 95%，引用覆盖率和回答忠实度不低于 90%；
- 局部缺失、全局拒答和无效引用处理正确率不低于 90%；
- 对照子集相对现有单轮 RAG 的质量下降不超过 5 个百分点；
- 所有运行在 90 秒内进入终态，模型调用不超过 1 次、检索不超过 20 次、证据不超过 24 个 chunk，并满足第 9 节 Token/字符预算；
- V1-V3 普通 RAG、健康报告和业务动作全量回归保持通过。

验收报告必须同时给出质量增益与成本变化。首个生产版本保持固定编排；只有后续新评估证明模型规划相对固定编排有显著收益时，才重新讨论范式。
