# V5 显式记忆的个人助手详细设计

> 状态：第一阶段范围与实现合同已批准，可按 Slices 1-7 连续实施；批准日期：2026-08-24；前置基线：V1、V2、V3 与 V4 第一阶段均已完成并通过验收。

## 1. 文档目的

V5 在现有单用户知识工作空间中增加经用户知情、可管理、可审计的跨会话记忆。第一阶段不追求自动理解所有用户信息，而是先完成一个边界清晰的场景：用户显式要求系统记住一条全局回答偏好，系统先保存强类型提案，用户独立确认后才写入；后续模型回答在固定预算内读取活动偏好，并向用户展示本次提供给模型的记忆。

本设计同时引入稳定的隐式单用户主体，但不实现登录。身份决定见 [ADR 0002](decisions/0002-use-implicit-single-user-subject.md)。

## 2. 用户场景

### 2.1 主场景

1. 用户在聊天中明确输入“请记住我的偏好：代码示例优先使用 Java”；
2. 服务端通过确定性规则识别 `BUSINESS_ACTION/CREATE_USER_MEMORY`，规范化并校验偏好内容；
3. 系统持久化待确认提案并展示操作卡片，此时没有记忆副作用；
4. 用户通过独立请求确认，服务端原子取得执行权并创建记忆；
5. 用户新建另一个会话并提出知识问题；
6. 系统在不降低检索、引用和拒答基线的前提下，把活动偏好作为受限、非证据上下文提供给模型；
7. 回答历史展示本次提供给模型的记忆，用户可以进入记忆管理页纠正、禁用或删除。

### 2.2 必须支持

- 显式创建全局回答偏好；
- 未确认时零副作用，重复或并发确认只创建一次；
- 跨会话读取活动偏好；
- 查看当前内容、来源、创建时间、更新时间、状态和可选过期时间；
- 纠正内容时保留历史版本，禁用或删除后不再进入新回答；
- 模型回答持久化本次实际提供的记忆版本，历史可解释；
- 用户可以在单次聊天请求中选择忽略全部长期记忆，但不能通过请求扩大记忆范围或指定其他用户。

## 3. 第一阶段不做什么

- 不实现登录、注册、密码、角色、JWT、OIDC、多用户或多租户；
- 不自动从普通聊天、文档、模型输出或行为统计中提取长期记忆；
- 不保存模型推测的用户事实，不保存事实型长期记忆，不把任务进度写成记忆；
- 不做向量化记忆、模型记忆分类、模型相关性选择或自动冲突合并；
- 不让记忆改变顶层路由、研究计划、工具范围、确认语义、引用校验或拒答结论；
- 不允许记忆成为文档事实的引用来源，不生成伪造的文档 citation；
- 不引入 Agent runtime、ReAct、LangGraph、MCP、多 Agent、动态工具或通用记忆框架；
- 不实现物理清除审计历史；普通删除继续遵循逻辑删除，未来 purge 必须是独立维护流程。

事实型长期记忆、知识库级作用域、自动候选提取和登录只属于后续候选，不因 V5 第一阶段获得授权。

## 4. 身份与访问边界

第一阶段新增 `CurrentSubjectProvider` 应用边界，返回稳定的 `UserSubject(id, key)`。生产默认实现 `LocalSingleUserSubjectProvider` 只返回数据库种子用户 `LOCAL_OWNER`。

- Controller 和客户端 DTO 不出现可写的 `ownerUserId`；
- 记忆查询与写入必须从 `CurrentSubjectProvider` 取得所有者并作为 Mapper 条件；
- 不允许从 Cookie、请求头、查询参数或模型输出覆盖当前主体；
- `LOCAL_OWNER` 是持久业务身份，不是 HTTP Session ID；
- 当前实现没有认证能力，所有能访问实例的人共享同一身份和记忆，部署只能限定在本机或可信网络；
- 将来登录适配必须先设计知识库、会话和其他资源的完整所有权迁移，本次只为用户记忆建立替换缝隙。

## 5. 能力与路由合同

顶层能力继续固定为 `SIMPLE_CHAT`、`KNOWLEDGE_QA` 和 `BUSINESS_ACTION`。

### 5.1 创建记忆

`CREATE_USER_MEMORY` 是 V5 第一阶段唯一新增的聊天业务动作。路由只匹配显式、版本化句式，例如：

- `请记住我的偏好：...`
- `记住回答偏好：...`

确定性解析器只截取显式前缀后的用户原文，执行 Unicode 规范化、首尾空白清理和连续空白折叠；内容长度为 1-300 字符，不允许空内容。没有明确“偏好”语义、只有“记住”措辞、附加执行指令或内容超限时，不创建提案，安全回落到澄清或 `KNOWLEDGE_QA`。第一阶段不调用模型分类或模型结构化提取。

提案参数固定为：

```json
{
  "memoryType": "RESPONSE_PREFERENCE",
  "scope": "GLOBAL",
  "content": "代码示例优先使用 Java",
  "expiresAt": null
}
```

服务器校验后保存参数，确认接口不接受覆盖。确认执行时再次解析当前主体并检查同一所有者下的活动内容哈希；完全相同的偏好幂等返回现有记忆，不创建重复记录。

### 5.2 读取记忆

`KNOWLEDGE_QA` 的普通 RAG 回答和 V4 `DOCUMENT_COMPARISON` 的最终 Synthesizer 可以读取回答偏好；确定性简单回复、健康报告、路由判断、动作提案和动作执行均不读取记忆。

请求可设置 `memoryMode = USE` 或 `IGNORE`，默认 `USE`。客户端不能指定记忆 ID、内容、用户 ID或预算。服务端只读取当前主体下 `ACTIVE`、未删除、未过期的全局回答偏好，按 `updated_at DESC, id DESC` 稳定排序，最多 10 条、合计最多 2000 字符；达到预算后停止追加并记录截断状态，不进行第二次模型调用。

记忆以独立 `<user_preferences>` 数据区加入 Prompt，并明确标记为用户提供但不可信的风格偏好：

- 只能影响语言、格式、示例语言、详细程度等表达方式；
- 不能覆盖系统指令、安全规则、知识库范围、研究计划或预算；
- 不能作为文档事实证据，不能产生文档 citation；
- 与当前明确请求冲突时，以当前请求为准；
- 与引用和拒答基线冲突时，以 grounding 规则为准。

## 6. 数据合同

计划使用下一条 Flyway 迁移建立以下结构；物理字段长度、索引名称和检查约束可在对应切片内细化，但不得改变语义。

### 6.1 `app_user`

- 保存稳定 UUID、业务键、显示名称、状态、时间戳和逻辑删除；
- 第一阶段只允许一条活动 `LOCAL_OWNER`；
- 该记录由迁移创建，不提供普通 CRUD API。

### 6.2 `user_memory`

- 保存所有者、固定类型 `RESPONSE_PREFERENCE`、固定作用域 `GLOBAL`、状态 `ACTIVE/DISABLED`、当前版本、可选 `expires_at`、创建/更新时间和逻辑删除；
- 活动内容的规范化 SHA-256 用于同一所有者内的精确去重，不做语义去重；
- 创建、重新启用和纠正时锁定当前 `app_user` 行，在同一事务内复核未删除/活动数量和活动内容哈希，避免并发突破数量或重复约束；
- 删除设置 `deleted = 1`，禁用保留记录但不再注入；过期记录不注入且不自动改写历史。

### 6.3 `user_memory_revision`

- 每次创建或纠正保存不可变版本号、规范化内容、内容哈希、来源类型、来源会话/消息、变更原因和时间；
- 纠正必须在一个事务中创建新版本并推进 `user_memory.current_revision`，不能原地覆盖旧内容；
- Chat 确认创建使用 `CHAT_CONFIRMED` 来源，管理页纠正使用 `MANAGEMENT` 来源；
- 普通 API 只返回当前版本，详情可返回不包含已删除敏感正文的版本摘要。

### 6.4 `message_memory_context`

- 保存助手消息、记忆、实际提供给模型的 revision、顺序和时间；
- 只记录真正进入 Prompt 的版本，便于历史恢复和解释；
- 记忆后续纠正、禁用或删除不会改写旧消息关联，但普通用户界面不得借历史关联重新暴露已删除正文。

### 6.5 `action_request` 扩展

- 静态允许 `CREATE_USER_MEMORY`；
- 参数 JSONB 只允许固定类型、全局作用域、受限内容和可选过期时间；
- 创建成功后的 `result_resource_id` 关联真实 `user_memory`；
- 继续复用 V2 的过期、拒绝、原子确认、幂等和脱敏失败语义。

## 7. 管理 API 与副作用

聊天创建继续走 `action_request` 提案与独立确认。记忆管理页中的纠正、禁用、启用和删除由用户直接操作专用资源接口，不由模型建议或触发；前端必须展示确认交互，后端使用强类型 DTO、当前主体过滤、版本号条件更新和审计 revision，避免丢失更新。

直接管理操作与聊天业务动作的区别是：前者由用户在专用管理界面明确提交目标和新值，不经过模型；后者来自自然语言聊天，必须先形成不可变提案再独立确认。任何模型输出都不能调用管理接口或代替用户点击。

## 8. API/SSE 合同摘要

计划新增：

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| `GET` | `/api/user-memories` | 查询当前隐式用户的活动、禁用和过期回答偏好 |
| `GET` | `/api/user-memories/{id}` | 查询当前版本、来源和版本摘要 |
| `PATCH` | `/api/user-memories/{id}` | 用户在管理页纠正内容、状态或过期时间，要求当前 `version` |
| `DELETE` | `/api/user-memories/{id}` | 用户确认后逻辑删除，重复删除幂等 |

聊天请求增加可选字段：

```json
{
  "memoryMode": "USE"
}
```

SSE 在 `route` 后、模型输出前增加可选 `memory_context` 事件，内容只包含记忆 ID、版本、受限摘要、数量、字符数和截断状态，不包含其他用户数据。没有活动记忆或 `memoryMode = IGNORE` 时不发送。历史助手消息返回可空 `memoryContext` 摘要。

## 9. 状态、失败与冲突语义

- `USER_MEMORY_NOT_FOUND`：当前主体范围内不存在；对其他主体资源同样返回 404；
- `USER_MEMORY_CONTENT_INVALID`：内容为空、超长或不满足规范化约束；
- `USER_MEMORY_VERSION_CONFLICT`：管理修改基于旧版本；
- `USER_MEMORY_DUPLICATE`：管理页尝试创建或纠正为同一活动内容；聊天确认则幂等返回现有记录；
- `USER_MEMORY_LIMIT_REACHED`：活动记忆达到固定上限，要求用户先管理现有记忆；
- `USER_MEMORY_CONTEXT_TRUNCATED`：只作为回答上下文摘要状态，不使回答失败；
- 记忆读取依赖失败时安全降级为不使用记忆的现有回答链路，并记录脱敏错误；不得降低 RAG 可用性；
- 记忆写入失败时 Action 进入 `FAILED`，不重试产生第二条记忆。

第一阶段固定最多 100 条未删除记忆、最多 20 条活动记忆；单次注入最多 10 条和 2000 字符。具体数据库约束必须与应用校验一致。

## 10. 前端合同

- `/chat` 展示记忆操作提案卡片，并在回答上展示可展开的“本次使用的偏好”；
- 输入区提供单次“忽略长期记忆”控制，默认使用；
- 新增 `/memories` 管理页，展示内容、状态、来源、更新时间和过期时间；
- 纠正、启用/禁用和删除都需要明确确认，删除文案说明当前采用逻辑删除且不会再用于新回答；
- 窄屏下记忆摘要和操作按钮不能水平溢出；
- 不展示或允许编辑 `ownerUserId`、内容哈希、内部 Prompt 或其他审计字段。

## 11. 安全与隐私边界

- 记忆内容和模型输出均视为不可信数据，不能转成命令、工具参数或路由决定；
- 日志只记录 memory ID、revision、数量、字符数、状态和 trace ID，不记录完整记忆正文；
- 记忆 Prompt 与文档证据使用不同标签，文档提示注入不能创建、修改或删除记忆；
- 用户当前请求优先于长期偏好，系统规则和 grounding 优先于二者；
- 没有登录意味着没有访问隔离，文档和页面必须持续明确“本机/可信网络单用户”限制；
- 前端隐藏字段不是安全边界，所有所有者、预算和状态校验都在服务端完成。

## 12. 评估合同

V5 在生产注入前建立 `v5-explicit-memory-v1` 固定数据集，至少包含：

- 12 个显式创建/非显式误触发案例；
- 8 个跨会话偏好生效与当前请求覆盖案例；
- 6 个提示注入、路由和 grounding 隔离案例；
- 12 个真实 PostgreSQL 生命周期案例，覆盖未确认、重复/并发确认、精确去重、纠正、禁用、过期、删除、版本冲突和历史恢复；
- V1-V4 全量回归以及普通回答/V4 研究各至少 4 个代表性真实模型案例。

固定阈值：

- 未确认副作用、隐式保存、模型自行保存、客户端指定所有者和越界读取均为 0；
- 显式路由、幂等、状态过滤、版本冲突、删除和过期案例 100% 通过；
- 单次注入不超过 10 条/2000 字符，预算超限为 0；
- 跨会话偏好遵循率不低于 90%，当前请求覆盖长期偏好正确率 100%；
- 记忆不能改变知识库范围、研究计划、引用或拒答结论，相关安全案例 100% 通过；
- V1-V4 全量回归保持通过。

真实用户记忆、私密聊天、密钥和未脱敏请求不得提交到评估资产。

## 13. 实施切片与授权

以下切片已经整体授权，可按顺序连续实施和独立验证，无需逐片重复请求授权：

1. **评估集与固定合同**：建立公开合成语料、路由/生命周期定义、预算和无记忆基线；不进入生产注入。
2. **隐式用户与记忆持久化**：实现 `CurrentSubjectProvider`、本地种子用户、Flyway、记忆聚合/版本和所有者过滤。
3. **创建偏好提案**：增加确定性显式意图、`CREATE_USER_MEMORY` 强类型参数、持久化提案、独立确认和幂等执行。
4. **管理 API 与页面**：查询、纠正、启用/禁用、过期和逻辑删除，完成来源与版本展示。
5. **受限记忆注入**：普通 RAG 与 V4 Synthesizer 按固定预算加载偏好，持久化 `message_memory_context`，支持单次忽略。
6. **SSE、历史与冲突闭环**：记忆上下文事件、断线/刷新恢复、版本冲突、过期和安全降级。
7. **评估与验收**：专项评估、Testcontainers、全量回归、真实 DeepSeek 链路、桌面/窄屏页面验收和版本报告。

每个切片必须保持可独立验证。机械字段可以在不改变本设计语义、预算、安全和失败边界的前提下细化；若 Slice 1 不能证明跨会话显式偏好相对无记忆基线的稳定收益，应停止扩大生产注入并先修订场景。

## 14. 完成标准

V5 第一阶段只有同时满足以下条件才能标记完成：

- 显式偏好提案、确认、幂等创建、管理和逻辑删除全部闭环；
- 隐式本地主体稳定且所有者完全由服务端确定；
- 普通 RAG 与 V4 研究在固定预算内使用偏好，简单回复和动作链路保持不变；
- 每条被注入的记忆版本可从回答历史追溯，删除后不再进入新回答；
- 固定评估、真实 PostgreSQL 生命周期、全量回归、前端构建、真实模型和页面验收均通过；
- 文档明确当前没有认证或多用户隔离，不把隐式主体宣传为登录功能；
- 不引入自动记忆、事实型记忆、模型规划、动态工具或未授权框架。
