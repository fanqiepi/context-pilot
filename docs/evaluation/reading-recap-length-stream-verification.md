# 回顾长度与断连清理修复

2026-10-23，acceptance-v17 / reading-evidence-v6。

## 现场结论

日常任务 `09f93b3d-45ad-43f7-9bce-bda9db7353dc` 为三章回顾，已持久化 FAILED / OUTPUT_INVALID / FACT_TEXT_LIMIT；实际输入/输出用量 5312/1340 token，finishReason=stop。按执行顺序，回答已通过 JSON 结构和引用 ID 校验，失败发生在全部事实文字累计超过 1200 Unicode 字符的检查。输出 token 数不等于文字字符数；历史任务未保存原文或字符计数，不能声称具体超了多少字。这条新失败也不能反推旧 JSON_SCHEMA 的原因。

用户日志同时给出独立的通知连接问题：`ReadingTaskEvents.poll` 捕获发送 IOException 后调用 close，close 再调用 SseEmitter.complete 刷新损坏响应，产生 AsyncRequestNotUsableException。异步异常进入全局 ApiExceptionHandler 后再次返回 JSON，出现 ApiErrorResponse 无法写入 text/event-stream 的二次错误。上轮只保护 ReadingHttpAdvice，没有覆盖本轮日志中的全局兜底路径及发送失败后的主动 complete，不能将上轮离线测试视为现场问题已全部修复。

## 改动与边界

- 发送 IOException 后只移除订阅，交由 Servlet 容器处理断连，不再主动完成/刷新损坏响应。
- 正常结束、超时、停机清理先原子移除订阅，避免重复完成；完成动作异常不逃出定时轮询，避免单连接故障中断其他订阅。非 IO 失败以 completeWithError 结束，且防护完成动作本身再次失败。
- 全局兜底识别不可用/断开的响应及已提交响应，不追加 JSON。未提交的普通 HTTP 错误仍返回原 INTERNAL_ERROR JSON。
- 用户在本轮明确反馈“回顾一百字左右已经够了”。回顾 Prompt v6 因此以约 100 字（通常 80–120 字）、2–3 条短要点为目标，简单窗口可更少；一至三章共用篇幅，只保留最近关键事件、人物当前处境和继续阅读最需记住的一件事。标点/数字/引文也计数，保留关键因果与限定。
- 服务端回顾硬上限同步从 1200 收紧为 160 Unicode 字符，为百字目标留少量余量；测试覆盖跨事实累计和 Unicode 边界。人物查证仍为 600。没有裁剪答案、二次生成或放宽引用校验；历史已完成长回答不重写，新的长度约束只用于新任务生成结果。
- 人物查证合同、历史失败记录、已读边界及本地开关不变。未改配置、前端、数据库结构，不新建 Application，不代启或调用真实模型。
