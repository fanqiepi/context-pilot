# ContextPilot 产品定位与大版本路线图

> 状态：V1 知识库问答基线、V2 可控行动助手、V3 知识库维护助手与 V4 第一阶段知识研究助手均已完成；V5 第一阶段显式记忆范围与 Slices 1-7 已批准，Slices 1-4 已完成，剩余切片可连续实施；V6 以后为方向性规划。

## 产品定位

ContextPilot 是一个学习型、可控、可评估的个人知识工作助手。

- 对用户而言，它以单用户知识库为工作空间，提供有依据、可追溯的问答，并在明确确认后执行受控业务操作。
- 对工程实践而言，它通过连续、可验收的用户场景逐步验证现代 Agent 能力，包括 grounding、能力路由、结构化输出、工具调用、human-in-the-loop、状态恢复、有限规划、显式记忆和外部工具互操作。
- 项目不以堆叠 Agent 框架为目标。任何框架、协议或运行时都必须由已经定义的用户场景、失败语义和评估标准驱动。

ContextPilot 当前不是通用聊天机器人、多租户 SaaS 或可自主访问任意系统的通用 Agent。模块化单体、单用户和后端可信执行边界仍是当前产品载体。

## 路线图治理

项目只使用 V1、V2、V3 等大版本表达路线，不再并行维护 P、N、I 或 A-D 等多套阶段编号。

- 已完成版本只保留结果摘要和未关闭的质量债务。
- 当前版本必须完整描述用户结果、范围、架构边界、数据、API、失败语义和验收标准。
- 下一版本只确定场景、候选能力、风险和进入条件；当前版本完成后才细化实现合同。
- 更远版本只描述目标和触发条件，不预选框架，也不构成实施授权。
- 每次开始新大版本前，必须同步更新 `AGENTS.md`、产品需求、技术架构、数据模型、API 和评估计划。

评估、trace、数据隔离、安全确认、失败处理、页面验收和发布检查是跨版本质量门槛，不是独立于产品能力之外的可选清理阶段。

## 稳定的顶层能力边界

当前聊天请求固定路由到三个版本化顶层能力：

- `SIMPLE_CHAT`：身份介绍、问候、能力说明、感谢和告别等确定性简单交互。
- `KNOWLEDGE_QA`：知识库隔离的检索、证据校验、拒答、引用和回答生成；未来的摘要、对比和学习提纲等知识任务原则上在该边界内演进。
- `BUSINESS_ACTION`：产生业务副作用的请求；必须先生成持久化提案，再由用户通过独立请求确认。

新增知识任务或业务动作通常应放在这三个顶层能力之下。只有后续场景证明现有边界无法清晰表达时，才评估增加新的顶层路由。

## V1：知识库问答助手（已完成）

用户可以创建知识库、上传 TXT/Markdown/文本型 PDF，在隔离的 PostgreSQL/pgvector 索引中检索，并获得带引用、可拒答、可流式传输和可恢复历史的回答。V1 同时完成固定顶层能力路由、模型调用与 trace 记录、正向反馈、Embedding profile 隔离和单文档重建索引。

V1 是后续版本必须保持的功能基线。对外发布前仍需持续检查限流、超时、取消、日志脱敏和恢复说明；后续版本的专项评估与页面验收不能替代这些发布检查。

## V2：可控行动助手（已完成）

V2 完成首个受控业务动作 `CREATE_KNOWLEDGE_BASE`：聊天只生成经过强类型校验并持久化的提案，用户必须通过独立请求确认，服务端再原子、幂等地调用 `KnowledgeBaseService`。提案状态、SSE 卡片、失败摘要、历史恢复、重复及并发确认均已实现并通过固定评估和页面验收。

V2 建立的提案、确认、幂等和审计协议继续适用于有副作用的动作，但不代表通用工具平台已经获批。完整证据见 [V2 版本验收报告](../evaluation/v2-acceptance-report.md)。

## V3：知识库健康检查与维护助手（已完成）

V3 完成知识库健康检查、不可变健康报告和单文档维护闭环。确定性健康路径通过 `KNOWLEDGE_QA/v2` 返回处理失败、索引缺失或 Embedding profile 异常；可信报告明细可以生成 `RETRY_DOCUMENT_PROCESSING` 或 `REINDEX_DOCUMENT` 提案，副作用继续复用 V2 的确认、幂等和审计协议。维护任务采用事务提交后派发和有界恢复扫描。

V3 的范围、迁移、切片和失败语义见 [V3 详细设计](../architecture/v3-knowledge-base-maintenance-design.md)，完成证据见 [V3 版本验收报告](../evaluation/v3-acceptance-report.md)。已完成范围不包含批量修复、自动动作链或通用工具网关。

## V4：知识研究助手（第一阶段已完成）

V4 第一阶段只交付显式 `DOCUMENT_COMPARISON`：用户在一个知识库内选择 2 至 5 份合格文档，系统使用版本化固定维度、逐文档有限只读检索、证据账本和一次最终综合生成可追溯比较。Slice 1 证明该场景需要范围化多步检索，但没有证明模型 Planner 优于固定编排，因此顶层能力仍为 `KNOWLEDGE_QA`，且不授权自主重规划、Agent 循环、LangGraph、MCP 或动态工具。

Slices 1-7、生产运行时、API/SSE、前端入口、全量回归和 DeepSeek/DashScope 端到端验收均已完成。研究综合不发送请求级 `max_tokens`，仍强制单次模型调用、90 秒硬超时、1800 字正文上限和 usage 记录。完整合同见 [V4 知识研究助手详细设计](../architecture/v4-knowledge-research-design.md)，证据见 [V4 实施验收报告](../evaluation/v4-implementation-acceptance-report.md)。

## V5：显式记忆的个人助手（第一阶段实施中）

V5 继续区分三类状态：

- 会话历史：过去发生了什么。
- 任务状态：当前任务进行到哪里。
- 用户记忆：经用户知情并可管理的稳定偏好或事实。

### 第一阶段用户结果

用户可以在聊天中显式要求系统记住一条全局回答偏好。系统必须先生成并持久化 `CREATE_USER_MEMORY` 强类型提案，用户通过独立请求确认后才创建记忆。后续普通 RAG 与 V4 最终综合可以在固定预算内读取活动偏好；用户可以查看来源和版本、纠正、启用/禁用、设置过期时间、删除，并在单次请求中忽略全部记忆。

### 身份决定

第一阶段使用稳定的隐式本地用户 `LOCAL_OWNER`，通过后端 `CurrentSubjectProvider` 获取，不实现登录、注册、密码、角色或多用户。客户端不能提交或覆盖用户 ID。该主体只提供稳定归属，不提供身份认证；当前实例只能用于本机或可信网络。未来加入登录时替换身份适配器，并另行设计知识库、会话和其他资源的完整所有权迁移。决定见 [ADR 0002](../architecture/decisions/0002-use-implicit-single-user-subject.md)。

### 固定范围

- 第一阶段只保存 `GLOBAL/RESPONSE_PREFERENCE`，内容为用户明确提供的 1-300 字符回答偏好；
- 不保存事实型长期记忆、任务状态、模型推测、普通聊天摘要或自动提取候选；
- 显式创建使用确定性路由与解析，不增加模型分类或模型结构化提取调用；
- 未确认零副作用，重复/并发确认幂等；管理页中的纠正、状态和删除只能由用户通过专用强类型 API 操作，模型不能调用；
- 单次注入最多 10 条、2000 字符，只能影响表达方式；不能改变知识库范围、引用、拒答、研究计划、预算、动作确认或工具边界；
- 简单确定性回复、健康报告、路由判断和动作执行不读取记忆；
- 记忆内容、版本、来源、状态和实际注入关系持久化并可审计，普通删除继续使用逻辑删除。

### 实施与验收

Slices 1-7 已整体批准：固定评估合同、隐式主体与持久化、创建提案、管理 API/页面、受限注入、SSE/历史/冲突闭环、最终验收。Slices 1-4 已完成并分别通过固定离线合同、PostgreSQL 持久化、可确认创建闭环和版本化管理闭环；剩余切片按顺序独立验证，无需逐片重复授权。下一批为 Slices 5+6，之后为 Slice 7；同批不代表合并检查点，每个 Slice 仍须保留独立提交和验收证据。

完整合同见 [V5 显式记忆详细设计](../architecture/v5-explicit-memory-design.md)。

V5 第一阶段的批准不授权登录、多用户、事实型记忆、自动记忆、向量记忆、模型规划、动态工具或通用 Agent runtime。

## V6：外部工具互操作（方向）

目标是在明确的知识工作场景下评估 MCP 等外部工具协议，例如读取经过授权的代码仓库、笔记或资料源。

外部协议只是接入方式，不是产品功能本身。首个连接必须服务于一个完整用户场景，并具有静态允许范围、最小权限、超时、结果来源、审计和撤销方式。V6 当前不授权插件市场、动态代码加载或任意外部工具访问。

进入条件：本地知识库和项目数据库无法满足一个稳定、可测试的用户任务，且目标外部系统和权限边界已经明确。

## 更远期探索：工作流与多 Agent

只有出现以下证据时才评估工作流引擎或多 Agent 模式：

- 任务确实需要多个可独立验证的步骤，并且显式应用服务已经难以维护。
- 子问题适合并行研究，或生成结果需要独立复核角色。
- 已具备步骤预算、循环上限、人工确认点、审计、恢复和评估集。

LangGraph、多 Agent 框架或其他运行时是届时的实现候选，不是预先承诺的路线目标。能力数量增长本身不能作为引入它们的理由。

## 跨版本安全与验收门槛

- 新能力必须先有明确用户场景、输入输出合同、失败语义和评估案例。
- 模型、检索文档和外部结果均为不可信输入，不能直接转成可执行命令。
- 副作用操作必须使用静态允许列表、强类型参数、最小权限、持久化提案、人工确认、幂等执行和审计记录。
- 只读结构化查询必须通过领域服务或专用 DataPort，使用参数绑定、字段白名单、限行、超时、来源和 `dataAsOf`；模型不能生成或执行 SQL。
- 新版本不得破坏知识库隔离、逻辑删除、引用可信性、拒答、SSE、历史和 trace ID 基线。
- 提示词、评估案例、数据库迁移、重要架构决定和版本验收报告都作为版本化项目资产。
