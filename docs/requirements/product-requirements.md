# ContextPilot 产品需求与路线图

> 状态：已确认的 MVP 基线与后续演进方向。后续路线仅用于规划，不代表已经授权实现 Agent、Skill 或工具调用；进入对应阶段前仍需明确用例、威胁模型和 ADR。

## 产品目标

ContextPilot 是一个面向学习和作品展示的单用户知识库与任务助手。MVP 的目标是完成从资料上传、向量检索到带引用流式回答的最小闭环，并保留可观察、可评估的工程资产。

产品演进遵循以下顺序：

1. 先把知识库 RAG 做正确、可引用、可追踪。
2. 再把固定能力组织成显式、可版本化的能力路由。
3. 确有结构化业务数据查询需求时，再增加白名单工具和项目数据库只读端口。
4. 只有固定流程无法满足已验证需求时，才评估更通用的 Agent 或工作流编排。

## 当前已完成基线

- 知识库 CRUD、业务表逻辑删除和 Knife4j 接口文档。
- TXT、Markdown、文本型 PDF 上传、解析、切分、状态、有限重试和本地文件存储。
- `PgVectorStore` 索引、知识库隔离检索、删除后的向量清理。
- 无需 API Key 的 `offline` Profile 和确定性 1024 维测试 Embedding。
- 文档摄取、检索和数据库迁移的自动化测试及本地测试夹具。

## MVP 核心流程

1. 创建、查看和逻辑删除知识库。
2. 上传 TXT、Markdown 或文本型 PDF。
3. 后台解析、切分、向量化并记录处理状态。
4. 用户在选定知识库和会话中提问。
5. 服务端检索相关分段并进行证据充分性检查；问题缺少必要上下文时返回澄清提示，无可靠依据时明确拒答。
6. 调用大模型生成受检索证据约束的回答。
7. 通过 SSE 返回增量内容和结构化引用，保存会话、消息、模型调用记录与反馈。

## MVP 功能范围

- 文档上传、状态查询、失败提示和有限重试。
- DashScope `text-embedding-v4`，固定 1024 维。
- PostgreSQL + pgvector 相似度检索。
- DeepSeek `deepseek-v4-flash` 流式回答。
- 简单的 `ChatApplicationService` 编排，不引入 Skill 路由或通用工具循环。
- 基于固定规则的请求校验、必要上下文澄清、无依据拒答和检索结果校验。
- 会话和消息历史、引用来源、模型调用记录、有用/无用反馈。
- 请求 ID/trace ID 在聊天、模型调用、SSE 错误和调用记录之间保持关联。
- 单用户、无登录，密钥仅由后端环境变量提供。

## MVP 剩余实施计划

| 优先级 | 阶段 | 主要交付 | 完成标准 |
| --- | --- | --- | --- |
| P0 | 摄取与检索基线 | 文档处理、离线 Embedding、pgvector 检索 | 已完成；自动化测试和 Knife4j 手工验证通过 |
| P1 | 真实 Embedding | 接入 DashScope `text-embedding-v4`、配置校验、重新索引说明 | 真实模型可完成文档入库和知识库隔离检索；密钥不进入 Git 或日志 |
| P2 | RAG 问答后端 | `conversation`、`chat_message`、`message_citation`、`model_call`；检索证据校验、提示词组装、DeepSeek 调用 | 单次非流式集成测试可得到有依据回答、引用或明确拒答 |
| P3 | SSE 与可观察性 | `/api/chat/stream`、增量事件、引用、usage、trace ID、失败状态落库 | 中断和失败可诊断；SSE 事件顺序稳定且不泄漏内部提示词或密钥 |
| P4 | 前端闭环 | 知识库与文档页面、独立聊天页面、历史消息、引用展示、处理状态与错误提示 | 用户可仅通过前端完成上传、提问、查看引用和历史记录 |

| P6 | MVP 加固 | 限流、超时、取消语义、日志脱敏、恢复说明和发布检查 | 达到本文验收标准，可形成可演示版本 |

## 后续演进路线

### 阶段 A：固定能力路由

- 将已稳定的能力定义为应用内、显式注册、可版本化的能力，例如“知识库问答”“文档摘要”“风险摘要”。
- 路由输入只使用受控的会话状态和请求字段；无法唯一匹配时返回澄清问题。
- 能力定义包含允许使用的数据来源、输入 Schema、提示词版本和输出契约。
- 仍然由模块化单体内的应用服务编排，不引入插件市场、动态脚本或自主多步 Agent。

进入条件：MVP 已稳定，至少存在两个确实需要不同输入契约或数据来源的固定能力。

### 阶段 B：受控工具执行网关

- 只有明确业务用例需要外部动作或结构化查询时才增加工具调用。
- 工具必须静态白名单注册，参数通过强类型 DTO 和 Schema 双重校验。
- 网关统一执行权限检查、次数限制、超时、错误分类、trace ID 和审计记录。
- 默认不自动重试有副作用操作；只读且幂等的工具才可按明确策略重试。
- 模型输出只是调用建议，不能绕过网关直接访问数据库、文件系统或网络。

进入条件：阶段 A 的固定能力无法仅通过 RAG 完成，并已完成工具级威胁模型、审计字段和失败恢复设计。

### 阶段 C：项目结构化数据查询

- 为特定场景增加领域化工具，例如 `DocumentProcessingSummaryQuery` 或 `ModelCallSummaryQuery`，而不是开放通用 SQL 工具。
- `DataPort` 对应项目自己的 `context_pilot` PostgreSQL，通过领域查询服务、Mapper 或只读视图访问。
- 查询使用只读事务、参数绑定、字段白名单、行数限制和超时，并遵守逻辑删除及知识库隔离规则。
- 结果统一携带来源、`dataAsOf`、质量/完整性说明和 trace ID。
- 模型不能直接获得 `DataSource`、Mapper 或 SQL 执行能力。

进入条件：存在明确、稳定、可测试的项目业务查询合同，且现有业务服务无法直接满足该能力。

### 阶段 D：Agent 或工作流评估

- 仅当需要跨多个受控能力进行多步规划，且固定编排的维护成本已经被数据证明过高时评估。
- 优先显式状态机和可回放步骤；不默认引入通用工作流引擎。
- 必须具备步骤级预算、循环上限、人工确认点、审计和评估集。

## 不在 MVP 范围内

- Skill Router/Registry、通用 ToolExecutionGateway、模型驱动的项目数据库查询、Agent 和工作流编排。
- 插件系统、动态代码或提示词驱动的任意工具调用。
- 多租户、注册登录、角色权限和计费。
- 消息队列、微服务或独立向量数据库。
- OCR、扫描 PDF、Office 文档和复杂表格恢复。

## MVP 验收标准

- 新开发者可按照文档启动依赖、后端和前端。
- 可完成一次知识库问答并看到可核查的引用。
- 缺少必要上下文时能够提示用户澄清；检索无可靠依据时不会编造答案。
- 模型或文档处理失败时展示可理解的状态和错误。
- 可查看模型、耗时、Token、状态、trace ID 和用户反馈。
- API Key、私密文档和完整敏感请求不进入 Git 或默认日志。
- 固定评估问题能够重复运行并用于对比配置变化。

## 后续阶段通用验收门槛

- 新能力必须先有明确用户场景、输入输出合同和失败语义。
- 新工具必须有白名单、强类型参数、最小权限、超时、调用上限和审计记录。
- 结构化查询结果必须展示来源和数据时间，不能让模型伪造来源。
- 架构扩展不得破坏现有 RAG 闭环、知识库隔离或逻辑删除约定。
