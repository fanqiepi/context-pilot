# ContextPilot 产品需求与路线图

> 状态：功能型 MVP 已完成；前端真实页面验收、固定评估基线和发布加固已延期。固定能力路由与首个需人工确认的业务操作已获准进入开发，Agent、LangGraph、通用工具框架和任意数据访问仍未授权。

## 产品目标

ContextPilot 是一个面向学习和作品展示的单用户知识库与任务助手。MVP 的目标是完成从资料上传、向量检索到带引用流式回答的最小闭环，并保留可观察、可评估的工程资产。

产品演进遵循以下顺序：

1. 先把知识库 RAG 做正确、可引用、可追踪。
2. 再把固定能力组织成显式、可版本化的能力路由。
3. 确有结构化业务数据查询需求时，再增加白名单工具和项目数据库只读端口。
4. 只有固定流程无法满足已验证需求时，才评估更通用的 Agent 或工作流编排。

## 当前已完成基线

- 知识库 CRUD、业务表逻辑删除和 Knife4j 接口文档。
- TXT、Markdown、文本型 PDF 上传、解析、切分、状态、有限重试和本地文件存储。
- `PgVectorStore` 索引、知识库隔离检索、删除后的向量清理。
- 无需 API Key 的 `offline` Profile 和确定性 1024 维测试 Embedding。
- 文档摄取、检索和数据库迁移的自动化测试及本地测试夹具。
- 已完成助手回答的单向“有用”反馈、取消标记和历史消息状态恢复。

## MVP 核心流程

1. 创建、查看和逻辑删除知识库。
2. 上传 TXT、Markdown 或文本型 PDF。
3. 后台解析、切分、向量化并记录处理状态。
4. 用户在选定知识库和会话中提问。
5. 服务端先处理固定白名单内的简单交互；其他问题检索相关分段并进行证据充分性检查，缺少必要上下文时返回澄清提示，无可靠依据时明确拒答。
6. 调用大模型生成受检索证据约束的回答。
7. 通过 SSE 返回增量内容和结构化引用，保存会话、消息、模型调用记录与反馈。

## MVP 功能范围

- 文档上传、状态查询、失败提示和有限重试。
- DashScope `qwen3.7-text-embedding`，固定 1024 维。
- PostgreSQL + pgvector 相似度检索。
- DeepSeek `deepseek-v4-flash` 流式回答。
- 简单的 `ChatApplicationService` 编排，不引入 Skill 路由或通用工具循环。
- 基于固定规则的请求校验、简单交互白名单、必要上下文澄清、无依据拒答和检索结果校验。
- 会话和消息历史、引用来源、模型调用记录和单向“有用”反馈。
- 请求 ID/trace ID 在聊天、模型调用、SSE 错误和调用记录之间保持关联。
- 单用户、无登录，密钥仅由后端环境变量提供。

## 当前已授权的下一阶段

目标是把现有单一 RAG 编排扩展为固定、可审计的三类能力路由：

```text
接收问题
  -> SIMPLE_CHAT：固定简单交互直接回答
  -> KNOWLEDGE_QA：执行现有知识库检索、证据校验和流式回答
  -> BUSINESS_ACTION：生成并持久化操作提案
                         -> 等待用户确认或拒绝
                         -> 确认后执行静态白名单业务操作
```

### N1：固定能力路由

- 定义 `SIMPLE_CHAT`、`KNOWLEDGE_QA`、`BUSINESS_ACTION` 三个显式、版本化能力。
- `SIMPLE_CHAT` 继续复用现有身份介绍、问候、能力说明、感谢和告别白名单，不扩展成开放域模型问答。
- `KNOWLEDGE_QA` 保留现有知识库隔离、证据阈值、拒答、引用、SSE、消息持久化和 trace ID 行为。
- 第一版按确定性优先级路由：简单交互白名单、明确业务操作规则、默认知识库问答。没有真实歧义数据前不增加额外的 LLM 分类调用。
- 路由结果包含能力 ID、版本、匹配依据和 trace ID；缺少业务参数或匹配不唯一时返回澄清，不猜测关键参数。

### N2：需确认的业务操作

- 首个授权业务操作为 `CREATE_KNOWLEDGE_BASE`，只允许通过强类型参数调用现有 `KnowledgeBaseService`。
- 业务请求首先生成服务端校验后的操作摘要和持久化提案，不能在该阶段创建知识库。
- 用户通过独立确认或拒绝请求作出决定；只有成功原子取得执行权的确认请求才能调用业务服务。
- 操作状态至少包含 `PENDING_CONFIRMATION`、`EXECUTING`、`SUCCEEDED`、`FAILED`、`REJECTED` 和 `EXPIRED`。
- 确认接口必须幂等；并发或重复确认不能重复创建知识库。失败只保存脱敏错误摘要，所有状态关联会话、消息和 trace ID。
- 前端以操作卡片展示类型、规范化参数、影响和状态，并提供“确认执行”“取消”按钮；刷新会话后仍可恢复当前状态。

### N3：当前阶段验收标准

- 原有简单回答、RAG、引用、历史和反馈自动化测试保持通过。
- 三类能力路由有确定性测试，普通知识问题不会误触发业务操作。
- 参数缺失会澄清，未经确认不会产生任何业务副作用。
- 确认、拒绝、过期、失败、重复确认和并发确认均有明确状态及测试。
- OpenAPI、Flyway、数据模型、前端类型和历史回显与实现同步。
- 不新增 LangGraph、Agent、消息队列、插件系统、任意 SQL 或通用外部工具能力。

## 后续演进路线

### 阶段 A：固定能力路由（已授权）

- 将已稳定的能力定义为应用内、显式注册、可版本化的能力，例如“知识库问答”“文档摘要”“风险摘要”。
- 路由输入只使用受控的会话状态和请求字段；无法唯一匹配时返回澄清问题。
- 能力定义包含允许使用的数据来源、输入 Schema、提示词版本和输出契约。
- 仍然由模块化单体内的应用服务编排，不引入插件市场、动态脚本或自主多步 Agent。

当前决策：产品方已将功能型 MVP 视为完成，并明确要求普通交互、知识问答和业务操作分流，因此阶段 A 已进入实施准备。

### 阶段 B：受控业务操作（首个切片已授权）

- 只有明确业务用例需要副作用时才增加业务操作；当前唯一批准的操作是创建知识库。
- 操作必须静态白名单注册，参数通过强类型 DTO 和服务端规则校验。
- 最小执行边界统一处理确认状态、幂等、超时、错误分类、trace ID 和审计记录，但不得提前抽象成支持任意工具的通用网关。
- 默认不自动重试有副作用操作；只读且幂等的工具才可按明确策略重试。
- 模型输出只是调用建议，不能绕过应用执行边界直接访问数据库、文件系统或网络。

当前决策：`CREATE_KNOWLEDGE_BASE` 用例与“确认后执行”的安全边界已经明确，允许与阶段 A 连续实施；增加第二个操作前必须再次确认具体用例和风险。

### 阶段 C：项目结构化数据查询

- 为特定场景增加领域化工具，例如 `DocumentProcessingSummaryQuery` 或 `ModelCallSummaryQuery`，而不是开放通用 SQL 工具。
- `DataPort` 对应项目自己的 `context_pilot` PostgreSQL，通过领域查询服务、Mapper 或只读视图访问。
- 查询使用只读事务、参数绑定、字段白名单、行数限制和超时，并遵守逻辑删除及知识库隔离规则。
- 结果统一携带来源、`dataAsOf`、质量/完整性说明和 trace ID。
- 模型不能直接获得 `DataSource`、Mapper 或 SQL 执行能力。

进入条件：存在明确、稳定、可测试的项目业务查询合同，且现有业务服务无法直接满足该能力。

### 阶段 D：Agent 或工作流评估

- 仅当需要跨多个受控能力进行多步规划，且固定编排的维护成本已经被数据证明过高时评估。
- 优先显式状态机和可回放步骤；不默认引入通用工作流引擎。
- 必须具备步骤级预算、循环上限、人工确认点、审计和评估集。

## 仍未授权的范围

- 通用 Skill/Capability 动态注册表、通用 `ToolExecutionGateway`、模型驱动的项目数据库查询、Agent、LangGraph 和其他工作流编排。
- 插件系统、动态代码或提示词驱动的任意工具调用。
- 任意 SQL、Shell、文件系统或 HTTP 工具，以及未逐项批准的副作用操作。
- 多租户、注册登录、角色权限和计费。
- 消息队列、微服务或独立向量数据库。
- OCR、扫描 PDF、Office 文档和复杂表格恢复。

## MVP 验收标准

- 新开发者可按照文档启动依赖、后端和前端。
- 可完成一次知识库问答并看到可核查的引用。
- 身份介绍、问候、能力说明、感谢和告别使用固定文案回复；除此之外，缺少必要上下文时能够提示用户澄清，检索无可靠依据时不会编造答案。
- 模型或文档处理失败时展示可理解的状态和错误。
- 可查看模型、耗时、Token、状态、trace ID，并可标记或取消回答的“有用”反馈。
- API Key、私密文档和完整敏感请求不进入 Git 或默认日志。
- 固定评估问题能够重复运行并用于对比配置变化。

## 后续阶段通用验收门槛

- 新能力必须先有明确用户场景、输入输出合同和失败语义。
- 新工具必须有白名单、强类型参数、最小权限、超时、调用上限和审计记录。
- 结构化查询结果必须展示来源和数据时间，不能让模型伪造来源。
- 架构扩展不得破坏现有 RAG 闭环、知识库隔离或逻辑删除约定。
