# ContextPilot 产品定位与大版本路线图

> 状态：V1 知识库问答基线已完成；V2 可控行动助手是当前唯一获准实施的版本；V3 仅确定知识库维护助手的场景雏形；V4 以后为方向性规划，不构成开发授权。

## 产品定位

ContextPilot 是一个学习型、可控、可评估的个人知识工作助手。

- 对用户而言，它以单用户知识库为工作空间，提供有依据、可追溯的问答，并在明确确认后执行受控业务操作。
- 对工程实践而言，它通过连续、可验收的用户场景逐步验证现代 Agent 能力，包括 grounding、能力路由、结构化输出、工具调用、human-in-the-loop、状态恢复、有限规划、显式记忆和外部工具互操作。
- 项目不以堆叠 Agent 框架为目标。任何框架、协议或运行时都必须由已经定义的用户场景、失败语义和评估标准驱动。

ContextPilot 当前不是通用聊天机器人、多租户 SaaS 或可自主访问任意系统的通用 Agent。模块化单体、单用户和后端可信执行边界仍是当前产品载体。

## 路线图治理

项目只使用 V1、V2、V3 等大版本表达路线，不再并行维护 P、N、I 或 A-D 等多套阶段编号。

- 已完成版本只保留结果摘要和未关闭的质量债务。
- 当前版本必须完整描述用户结果、范围、架构边界、数据、API、失败语义和验收标准。
- 下一版本只确定场景、候选能力、风险和进入条件；当前版本完成后才细化实现合同。
- 更远版本只描述目标和触发条件，不预选框架，也不构成实施授权。
- 每次开始新大版本前，必须同步更新 `AGENTS.md`、产品需求、技术架构、数据模型、API 和评估计划。

评估、trace、数据隔离、安全确认、失败处理、页面验收和发布检查是跨版本质量门槛，不是独立于产品能力之外的可选清理阶段。

## 稳定的顶层能力边界

当前聊天请求固定路由到三个版本化顶层能力：

- `SIMPLE_CHAT`：身份介绍、问候、能力说明、感谢和告别等确定性简单交互。
- `KNOWLEDGE_QA`：知识库隔离的检索、证据校验、拒答、引用和回答生成；未来的摘要、对比和学习提纲等知识任务原则上在该边界内演进。
- `BUSINESS_ACTION`：产生业务副作用的请求；必须先生成持久化提案，再由用户通过独立请求确认。

新增知识任务或业务动作通常应放在这三个顶层能力之下。只有后续场景证明现有边界无法清晰表达时，才评估增加新的顶层路由。

## V1：知识库问答助手（已完成）

### 用户结果

用户可以创建知识库、上传并处理文档，在选定知识库中获得带引用的流式回答，恢复会话历史，并标记回答是否有用。

### 已完成能力

- 知识库 CRUD、业务表逻辑删除和 Knife4j 接口文档。
- TXT、Markdown、文本型 PDF 上传、解析、切分、状态、有限重试和本地文件存储。
- PostgreSQL、`PgVectorStore`、知识库隔离检索和删除后的向量清理。
- DashScope `qwen3.7-text-embedding` 真实链路及无需 API Key 的确定性离线 Embedding。
- DeepSeek `deepseek-v4-flash` 非流式与 SSE 问答、证据校验、无依据拒答和结构化引用。
- 会话、消息、引用、模型调用、trace ID 和正向“有用”反馈。
- `SIMPLE_CHAT`、`KNOWLEDGE_QA`、`BUSINESS_ACTION` 三类固定能力路由及其持久化回显。
- Embedding profile 追踪、向量空间隔离、兼容性展示和单文档重建索引。

### 延续到后续版本的质量债务

- 在真实后端链路上完成前端页面级验收。
- 建立可公开提交的固定评估集和可重复基线报告。
- 在对外发布前完成限流、超时、取消语义、日志脱敏、恢复说明和发布检查。

这些事项不改变 V1 功能基线已经完成的结论，但必须纳入后续版本的验收门槛，不能被误写为已完成或取消。

## V2：可控行动助手（当前授权）

### 版本目标

让用户能够在聊天中提出“创建知识库”请求，先看到经过服务端校验的操作提案，明确确认后才执行真实创建操作，并能在刷新会话后恢复提案及最终状态。

V2 用一个完整动作建立最小、可靠的工具调用与 human-in-the-loop 基线，不建设通用 Agent 或工具平台。

> 实现进度（2026-08-13）：核心纵向链路已经落地，包括提案持久化、状态机、查询/确认/拒绝接口、过期处理、原子幂等执行、SSE、历史恢复和前端操作卡片；确认、取消和刷新恢复已通过本地真实页面验收。固定操作评估基线尚未建立，因此 V2 仍是当前版本，尚未宣告完成。

### 当前动作

- 动作类型：`CREATE_KNOWLEDGE_BASE`。
- 参数：规范化后的知识库名称和可选描述。
- 执行边界：静态应用动作调用现有 `KnowledgeBaseService`。
- 用户确认：必须通过独立确认请求，聊天文本和模型输出不能视为确认。

### 必须实现

- 业务请求的确定性识别、参数解析、缺失参数澄清和强类型服务端校验。
- 经校验的操作摘要和持久化 `action_request` 提案。
- `PENDING_CONFIRMATION`、`EXECUTING`、`SUCCEEDED`、`FAILED`、`REJECTED`、`EXPIRED` 状态。
- 独立查询、确认和拒绝接口。
- 带期望状态的原子执行权获取；重复或并发确认不能重复创建知识库。
- 会话、用户消息、助手提案消息、能力版本、动作类型和 trace ID 的可信关联。
- 前端操作卡片，展示规范化参数、影响、过期时间和后端状态，并支持确认、取消与历史恢复。
- 可预期失败和内部异常的安全摘要，不暴露堆栈、SQL、密钥或完整模型请求。

### 明确不包含

- 第二个业务动作、批量动作或动作链。
- 通用 Skill/Capability 动态注册表、通用 `ToolExecutionGateway` 或插件系统。
- LangGraph、Agent 自主循环、MCP、模型生成 SQL，以及任意 Shell、文件或 HTTP 工具。
- 模型替代用户确认，或在提案持久化前执行副作用。

### 完成标准

- 原有简单交互、RAG、引用、历史和反馈回归测试保持通过。
- 普通知识问题和复合措辞不会误触发创建知识库。
- 空名称、超长名称、名称冲突和客户端参数篡改具有稳定失败语义。
- 未确认、已拒绝和已过期提案不产生副作用。
- 确认、拒绝、过期、执行失败、重复确认和并发确认均有自动化测试。
- OpenAPI、Flyway、数据模型、前端类型、SSE 和历史回显与实现同步。
- 完成真实页面链路验收，并建立覆盖路由与操作安全性的固定评估案例。

## V3：知识库健康检查与维护助手（场景雏形）

> V3 尚未授权实施。V2 完成并复盘后，才允许细化 V3 的请求合同、持久化结构和前端交互。

### 用户场景

用户可以要求助手检查当前知识库是否存在处理失败、索引缺失或 Embedding profile 过期等问题。助手先给出有来源的健康摘要和修复建议；需要副作用的修复仍然生成独立提案，并等待用户确认。

示例：

```text
用户：检查这个知识库有没有异常。

助手：
1. 两个文档处理失败；
2. 一个文档使用旧的 Embedding profile；
3. 建议重试失败文档，并为过期文档重建索引；
4. 等待用户选择并确认操作。
```

### 候选固定能力

- `GET_KNOWLEDGE_BASE_HEALTH`：通过领域化只读查询返回文档状态、索引兼容性、数据时间和来源说明。
- `RETRY_DOCUMENT_PROCESSING`：为满足当前重试条件的失败文档提交处理任务。
- `REINDEX_DOCUMENT`：为来源未知或 profile 过期的成功文档提交重建索引任务。

`GET_KNOWLEDGE_BASE_HEALTH` 是只读能力；重试和重建是业务动作，必须复用 V2 的提案、确认、幂等和审计边界。动作成功只表示任务被可靠提交，文档处理的最终结果仍由文档状态表达。

### 进入条件

- V2 状态机、确认协议和前端操作卡片通过验收。
- 通过 V2 复盘确认哪些代码可以共享，不能提前抽象通用工具网关。
- 明确知识库健康结果的字段、来源、`dataAsOf`、完整性说明和知识库隔离规则。
- 明确重名文档、多候选目标、异步提交失败和后台处理失败的交互语义。

## V4：知识研究助手（方向）

目标是在 `KNOWLEDGE_QA` 边界内支持带引用的指定文档摘要、多文档对比、主题概览和学习提纲。

只有单次固定编排无法满足已经验证的知识任务时，才评估有限步骤规划。任何规划能力都必须具备步骤上限、Token/时间预算、中间状态、取消语义、来源约束和可回放评估。V4 当前不预选 LangGraph 或其他工作流框架。

进入条件：V3 完成，且固定评估数据表明至少一个知识研究任务需要多步检索或中间结果，而不是通过一次受控服务调用即可完成。

## V5：显式记忆的个人助手（方向）

目标是区分三类状态：

- 会话历史：过去发生了什么。
- 任务状态：当前任务进行到哪里。
- 用户记忆：经用户知情并可管理的稳定偏好或事实。

长期记忆必须具备来源、创建时间、更新时间、查看、纠正和删除入口。不得把全部聊天记录自动提升为长期记忆，也不得将模型推测保存为用户事实。

进入条件：出现跨会话重复提供同一偏好或任务背景的真实用例，并能够建立记忆正确性、过期和删除评估。

## V6：外部工具互操作（方向）

目标是在明确的知识工作场景下评估 MCP 等外部工具协议，例如读取经过授权的代码仓库、笔记或资料源。

外部协议只是接入方式，不是产品功能本身。首个连接必须服务于一个完整用户场景，并具有静态允许范围、最小权限、超时、结果来源、审计和撤销方式。V6 当前不授权插件市场、动态代码加载或任意外部工具访问。

进入条件：本地知识库和项目数据库无法满足一个稳定、可测试的用户任务，且目标外部系统和权限边界已经明确。

## 更远期探索：工作流与多 Agent

只有出现以下证据时才评估工作流引擎或多 Agent 模式：

- 任务确实需要多个可独立验证的步骤，并且显式应用服务已经难以维护。
- 子问题适合并行研究，或生成结果需要独立复核角色。
- 已具备步骤预算、循环上限、人工确认点、审计、恢复和评估集。

LangGraph、多 Agent 框架或其他运行时是届时的实现候选，不是预先承诺的路线目标。能力数量增长本身不能作为引入它们的理由。

## 跨版本安全与验收门槛

- 新能力必须先有明确用户场景、输入输出合同、失败语义和评估案例。
- 模型、检索文档和外部结果均为不可信输入，不能直接转成可执行命令。
- 副作用操作必须使用静态允许列表、强类型参数、最小权限、持久化提案、人工确认、幂等执行和审计记录。
- 只读结构化查询必须通过领域服务或专用 DataPort，使用参数绑定、字段白名单、限行、超时、来源和 `dataAsOf`；模型不能生成或执行 SQL。
- 新版本不得破坏知识库隔离、逻辑删除、引用可信性、拒答、SSE、历史和 trace ID 基线。
- 提示词、评估案例、数据库迁移、重要架构决定和版本验收报告都作为版本化项目资产。
